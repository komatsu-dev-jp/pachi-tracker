## 換金率対応の計算契約

`rotation` と `equivalentBorder` は250玉あたりの回転数として扱う。

```text
払出価値/回転 = 250000 / (equivalentBorder × exRate)

投入費用/回転 =
  250000 / rotation
  × (cashRatio / rentBalls + nonCashRatio / exRate)

EV/回転 = 払出価値/回転 - 投入費用/回転

実質ボーダー =
  equivalentBorder
  × (cashRatio × exRate / rentBalls + nonCashRatio)
```

必須境界:

- 等価 `rentBalls=250, exRate=250` では従来の等価計算と一致する。
- 非等価 `exRate=280` では、現金比率があるほど実質ボーダーが上がる。
- `rotation = 実質ボーダー` なら、現金・混合・持ち玉の各比率でEVが0になる。

## バックテストと校正の安全策

- 同じ日の再取込が複数ある場合は、その日を答え合わせから除外する。
- 前日と翌日が連続日である組だけを使う。
- 20件未満では `muraCoef` の候補値を出さない。
- 20件以上でも「提案のみ」とし、機種マスタを自動更新しない。
- biasは「予測 − 実測」。プラスなら予測が強気だったことを表す。

## 中10: 実戦観測の単位規約

`deriveFromRows()` の現行契約では、持ち玉・貯玉のK数は
`ballsConsumed / rentBalls` で作られている。したがって
`cashKCount + mochiKCount + chodamaKCount` を `rentBalls` 倍すると、
全モードの物理投入玉数へ戻せる。

`practiceObservation()` は次の変換を行う。

```text
250玉基準の回転率 = start1K × 250 / rentBalls
物理投入玉数       = 合計K数 × rentBalls
```

250玉貸しの20回/Kと、280玉貸しの22.4回/Kを同じ20回/250玉・同じ2,500投入玉として扱う統合テストを置く。

なお、`logic.js` 内の持ち玉「円価値」の式は別の既知疑義であり、今回の保護範囲では変更しない。戦略マップの新しい期待値計算は `economics.js` の独立した共通関数で扱う。
