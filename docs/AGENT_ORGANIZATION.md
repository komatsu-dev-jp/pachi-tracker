# PachiTracker の Codex 部署構成

## 結論

Codex の親エージェントが司令塔です。専門役（部署）は、同時に進めても速さまたは品質が上がる場合だけ起動します。小さな確認、説明、1ファイルの軽い修正は、司令塔だけで完結させます。

## 部署と担当範囲

| 部署 | カスタムエージェント | 役割 | 権限 |
| --- | --- | --- | --- |
| 調査 | `pachi_explorer` | 関連コード、実行経路、既存テスト、保護対象を調べる | 読み取り専用 |
| 設計 | `pachi_architect` | 曖昧または高リスクな要望を、完了条件つきの実装計画にする | 読み取り専用 |
| 定型実装 | `pachi_routine_worker` | 範囲が明確な小さな変更を実装・テストする | プロジェクト内で編集可 |
| 統合実装 | `pachi_integration_worker` | React の状態、保存層、複数ファイルにまたがる計画を実装する | プロジェクト内で編集可 |
| 品質保証 | `pachi_verifier` | 実装者とは別にテスト、lint、build、画面確認をする | 検証成果物以外は変更しない |
| 最終レビュー | `pachi_reviewer` | データ、計算、保存互換性、PWA、セキュリティの回帰を独立確認する | 読み取り専用 |
| 知識管理 | `pachi_memory_curator` | 検証済みの失敗と再発防止策を `memory/` に整理する | `memory/` のみ編集可 |

## 任せる基準

Plan mode（複数工程の作業を先に整理するモード）を使うのは、要望が曖昧、複数工程、複数領域、または高リスクの場合です。サブエージェントを起動できるのは、次をすべて満たす場合です。

1. 少なくとも2つの独立した作業がある。
2. お互いの完了を待たず並行して進められる。
3. 同じファイルを書き換えない。
4. それぞれに確認可能な完了条件がある。
5. 依頼・引き継ぎの手間より、速度または品質の向上が大きい。

同じコード領域は必ず1人の実装担当が所有します。品質保証と最終レビューは、動作、データ、設定、セキュリティ、または複数領域をまたぐ変更で使います。

## モデルの使い分け

| 作業 | モデル | 思考量 |
| --- | --- | --- |
| 設計、最終レビュー、memory の昇格判断 | GPT-5.6 Sol | high |
| 調査、定型実装、統合実装、検証 | GPT-5.6 Terra | low〜high |

親エージェントでユーザーが明示したモデルや思考量は変更しません。利用できないモデルを仮定せず、環境にあるモデルへ安全に切り替えます。

## 基本の流れ

1. 司令塔が `AGENTS.md`、`memory/INDEX.md`、作業ツリー、実際の検証コマンドを確認する。
2. 必要な場合だけ調査役と設計役を分け、対象ファイルと完了条件を確定する。
3. 実装担当は担当範囲だけを変更し、関係するテストを実行する。
4. 重要な変更は検証役、必要に応じて最終レビュー役が独立確認する。
5. 再利用できる失敗知見だけを memory 管理役が記録する。

このアプリの通常検証は `npm test`、`npm run lint`、`npm run build`、`git diff --check` です。UI 変更では 393×852 と幅 320px の画面確認も行います。
